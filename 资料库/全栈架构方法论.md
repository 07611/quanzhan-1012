# 全栈架构方法论：从一句话想法到可执行架构

> 配套「FullStack Architect 全栈架构工作台」的方法论文档。工作台把本文的流程做成了可点击的工具，本文解释每一步背后的判断依据。

## 一、四步法总览

```
一句话想法  →  ① 拆需求  →  ② 划边界  →  ③ 五层选型  →  ④ 最小闭环验证
```

绝大多数烂尾项目，不是死在技术难度，而是死在**跳过①②直接写代码**。

---

## 二、第一步：把想法拆成「角色 + 对象 + 动作」

用一句话模板重写你的想法：

> **谁** 要对 **什么对象** 做 **什么动作**。

例：校园二手交易平台

| 角色 | 对象 | 动作 |
|---|---|---|
| 游客 | 商品 | 浏览、搜索 |
| 学生 | 商品 | 发布、下架、编辑 |
| 学生 | 订单 | 下单、查看 |
| 学生 | 私信 | 发送、已读 |
| 管理员 | 内容 | 审核、下架、处理举报 |

**判断标准**：每一个「动作」背后都应该对应**一张数据表**和**一组接口**。写不出表名，说明这个动作还没想清楚。

---

## 三、第二步：划清系统边界

必须明确回答三个问题：

1. **本期做**：列出不超过 6 个核心功能
2. **本期不做**：明确写出来（如「暂不做支付，先用线下转账」）
3. **交给第三方**：支付、短信、对象存储、地图、地图定位

> 边界不清是需求蔓延的根源。「顺便再加个……」（顺便加评论、顺便加积分、顺便加推荐算法）是项目失控的头号信号。

---

## 四、第三步：五层选型

| 层 | 职责 | 不该管的 |
|---|---|---|
| 前端 | 展示、交互、表单体验、路由 | 业务规则、权限判定 |
| 后端 | 鉴权、业务规则、校验、事务 | 拼 SQL 字符串、泄露表结构 |
| 数据 | 持久化、索引、约束、迁移 | 业务逻辑（存储过程能少则少） |
| 安全 | 传输加密、输入校验、限流、日志（横切） | 当成上线前的补丁步骤 |
| 部署 | 构建、发布、回滚、监控 | 让环境差异影响运行结果 |

### 选型的三条原则

1. **一人项目优先一套语言打通全栈**（TS + Next.js，或 Python + FastAPI + 轻前端）
2. **团队 > 5 人再考虑多语言 / 多服务**，否则运维成本吃掉全部收益
3. **选「能快速做完」的，不选「最火的」**——练手项目的第一目标是跑通上线

---

## 五、第四步：最小闭环验证

不要横向铺功能，先纵向打通**最窄的一条完整链路**：

```
注册 → 登录 → 增删改查一条数据 → 部署上线
```

这条链路跑通之前，加任何功能都是在给未验证的地基上堆砖。

### 链路检查清单

- [ ] 前端能真实调通后端接口（不是 mock）
- [ ] 后端能真实读写数据库（不是内存数组）
- [ ] 未登录访问受保护接口返回 401
- [ ] 越权访问他人资源返回 403
- [ ] 刷新页面后数据仍在
- [ ] 线上地址能打开，且是 HTTPS

## 六、数据流：任何一环缺失都会暴露

```
浏览器
  → 前端路由
  → API 请求（带凭证）
  → 后端鉴权中间件
  → 业务服务层
  → 数据访问层（ORM / SQL）
  → 数据库
  ← 逐层返回
```

| 现象 | 最可能缺失的环节 |
|---|---|
| 页面空白 | 前端路由或渲染错误 |
| 接口 401 | 鉴权中间件未放行 / 凭证未带 |
| 接口 403 | 资源归属校验过严或过松 |
| 接口 500 | 环境变量缺失 / 空值解构 / 事务未回滚 |
| 接口 200 但数据不落库 | 忘了 `await` / 事务未提交 / 连到了另一个库 |
| 跨域报错 | 后端未配 CORS / 未用同域反代 |

## 七、常见失衡（对照自查）

| 失衡 | 表现 | 纠正 |
|---|---|---|
| 选型堆砌 | 个人项目上微服务 + K8s | 退回单体 + 托管平台 |
| 只做前端 | 接口全写死 mock | 先补后端最小接口 |
| 忽略安全 | 上线后才发现能看别人数据 | 每个接口加资源归属校验 |
| 没有部署 | 本地跑通就当完成 | 第一天就部署一个空壳上线 |
| 需求蔓延 | 「顺便再加个……」 | 写死本期不做清单 |
| 无迁移管理 | 手改生产库结构 | 所有变更走迁移文件并进 Git |
