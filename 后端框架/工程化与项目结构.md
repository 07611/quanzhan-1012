# 后端工程化与项目结构

## 一、推荐分层

```
server/
├── index.ts            入口：装配中间件、挂载路由、启动监听
├── routes/             路由声明：只做「路径 → 控制器」的映射
├── controllers/        控制器：解析请求、调用服务、组装响应
├── services/           业务逻辑：事务、规则校验、领域计算
├── repositories/       数据访问：只与数据库打交道
├── models/             实体定义 / ORM schema
├── middleware/         鉴权、校验、限流、错误处理
├── dtos/               入参出参结构与校验规则
├── config/             配置读取与环境校验
└── utils/              纯函数工具
```

### 分层铁律

| 层 | 可以做 | 不允许做 |
|---|---|---|
| routes | 声明路径、挂中间件 | 写业务逻辑 |
| controllers | 取参数、调服务、返回响应 | 直接访问数据库 |
| services | 业务规则、事务编排 | 感知 HTTP 请求对象 |
| repositories | 查询与写入 | 业务判断 |

> 判断标准：**services 不应该 `import` 任何 HTTP 相关的类型**。如果需要，说明分层漏了。

## 二、统一响应结构

```json
{ "code": 0, "message": "ok", "data": { } }
```

| code | 含义 | HTTP 状态码 |
|---|---|---|
| 0 | 成功 | 200 |
| 40000 | 参数校验失败 | 422 |
| 40100 | 未登录 / 令牌无效 | 401 |
| 40300 | 无权限 / 越权 | 403 |
| 40400 | 资源不存在 | 404 |
| 42900 | 请求过于频繁 | 429 |
| 50000 | 服务器内部错误 | 500 |

**为什么业务码与 HTTP 码分开**：前端需要区分「网络层失败」与「业务层失败」，混在一起会让错误处理变成一堆状态码判断。

---

## 三、错误处理中间件

```
请求进入
  → 业务抛出自定义 AppError(code, message, status)
  → 全局错误中间件捕获
      · 已知错误：返回 code + 可读 message
      · 未知错误：记录堆栈到日志，对外只返回 50000 + 「服务异常」
```

**绝对不要**把数据库堆栈、SQL 语句、文件路径返回给前端。

---

## 四、参数校验

**入参必须在入口校验，且校验失败要给出字段级错误**：

```json
{
  "code": 40000,
  "message": "参数校验失败",
  "data": { "email": "邮箱格式不正确", "password": "长度至少 8 位" }
}
```

| 语言 | 工具 |
|---|---|
| TypeScript | zod / class-validator + class-transformer |
| Python | Pydantic（FastAPI 内置） |
| Java | Jakarta Bean Validation (@Valid) |
| Go | go-playground/validator |

## 五、日志

**结构化日志**（JSON），至少包含：时间、级别、请求 ID、路径、耗时、状态码、用户 ID。

```
{"t":"2026-09-25T14:38:03Z","level":"info","rid":"a1b2c3","method":"POST","path":"/api/v1/orders","ms":42,"status":201,"uid":128}
```

**规则**：
- 每个请求生成唯一 `requestId`，贯穿全链路，便于定位
- 日志级别：`debug` 开发 / `info` 关键动作 / `warn` 可恢复异常 / `error` 需人工介入
- **绝不**打印密码、令牌、身份证等敏感字段

## 六、配置管理

```
config/
├── index.ts        统一出口，集中读取与校验
└── schema.ts       启动时校验必需的环境变量，缺失则直接退出
```

**启动即校验**：缺少 `DATABASE_URL` 或 `JWT_SECRET` 时，服务应该**启动失败并打印清晰提示**，而不是运行到某个接口调用时才崩。

| 环境 | 文件 |
|---|---|
| 开发 | `.env.development` |
| 测试 | `.env.test` |
| 生产 | 由部署平台注入环境变量，**不落盘** |

---

## 七、数据库与迁移

- 所有结构变更写**迁移文件**并进 Git，禁止手工改生产库
- 迁移必须**可回滚**（提供 down）
- 种子数据（seeds）只用于开发与演示，不要混进生产
- 生产改结构前先备份，大表加索引注意锁表

---

## 八、测试

| 类型 | 覆盖对象 | 工具（TS） |
|---|---|---|
| 单元测试 | 纯函数、服务逻辑（mock 仓储） | Vitest / Jest |
| 集成测试 | 服务 + 真实数据库（测试库） | Jest + supertest |
| 端到端 | 关键用户路径 | Playwright |

**优先级**：把测试预算花在**鉴权、权限校验、金额计算、状态机流转**这四类逻辑上，它们的缺陷代价最高。

---

## 九、上线前检查

- [ ] 所有接口在未登录时的行为已确认（401 而非 500）
- [ ] 每个涉及资源的接口都校验了资源归属
- [ ] 列表接口全部服务端分页
- [ ] 慢查询已加索引（用 `EXPLAIN` 验证）
- [ ] 错误响应不含堆栈与 SQL
- [ ] 敏感配置全部来自环境变量
- [ ] 日志有 requestId，可串联一次请求
- [ ] 数据库端口未暴露公网
