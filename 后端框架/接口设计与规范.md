# 接口设计与规范

## 一、REST 命名约定

| 动作 | 方法 | 路径 | 说明 |
|---|---|---|---|
| 列表 | GET | `/api/v1/items` | 支持分页、筛选、排序 |
| 详情 | GET | `/api/v1/items/:id` | 单个资源 |
| 新建 | POST | `/api/v1/items` | 请求体为资源字段 |
| 全量更新 | PUT | `/api/v1/items/:id` | 幂等 |
| 局部更新 | PATCH | `/api/v1/items/:id` | 只传要改的字段 |
| 删除 | DELETE | `/api/v1/items/:id` | 软删除或硬删除 |

### 命名规则

- 资源用**复数名词**：`/users`、`/orders`（不要 `/getUser`）
- 层级关系用嵌套：`/posts/:id/comments`
- 非 CRUD 动作用子资源或动词后缀：`/orders/:id/cancel`、`/auth/login`
- 统一版本前缀 `/api/v1`，为不兼容变更留后路

## 二、统一响应结构

### 成功

```json
{ "code": 0, "message": "ok", "data": { "id": 1, "title": "…" } }
```

### 分页

```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "list": [ ],
    "page": 1,
    "pageSize": 20,
    "total": 137,
    "hasMore": true
  }
}
```

### 失败

```json
{ "code": 40000, "message": "参数校验失败", "data": { "email": "邮箱格式不正确" } }
```

## 三、分页：offset 还是游标

| 方式 | 适用 | 风险 |
|---|---|---|
| `page` + `pageSize`（offset） | 后台管理、数据量可控 | 深分页性能断崖（`OFFSET 100000`） |
| `cursor` 游标 | 信息流、无限滚动 | 不能跳页 |

**规则**：
- 后台表格用 offset
- 无限滚动、信息流用游标（`WHERE id < cursor ORDER BY id DESC LIMIT 20`）
- **任何列表都不允许一次性返回全量数据**

## 四、鉴权

```
Authorization: Bearer <token>
```

| 场景 | 返回 |
|---|---|
| 未带凭证 | 401（提示「请先登录」） |
| 凭证过期 / 无效 | 401（前端应触发刷新令牌或跳登录） |
| 已登录但无权限 | 403（提示「无权访问该资源」） |
| 资源不属于当前用户 | 403（**不要返回 404**，避免泄露资源是否存在） |

**最重要的纪律**：**每个涉及资源的接口都要校验资源归属**。只判断「是否登录」不判断「是否是我的数据」，是最常见也最致命的漏洞。

## 五、幂等性

以下接口必须幂等（重复调用不产生脏数据）：

- 支付回调
- 点赞 / 取消点赞
- 关注 / 取关
- 报名（同一用户同一活动只能有一条有效记录）
- 创建订单（用客户端生成的 `idempotencyKey` 去重）

实现方式：数据库唯一索引 + 「存在则忽略」，或 Redis 记 `SETNX` 短时标记。

## 六、并发与超卖

名额类、库存类数据**禁止「先查后写」**：

```sql
-- 错误：并发下会超卖
SELECT booked_count FROM slots WHERE id = 1;
UPDATE slots SET booked_count = <查到的值 + 1> WHERE id = 1;

-- 正确：数据库原子更新，并检查影响行数
UPDATE slots
   SET booked_count = booked_count + 1
 WHERE id = 1 AND booked_count < capacity;
-- affectedRows === 0 → 名额已满，返回业务错误码
```

## 八、接口设计自查清单

- [ ] 路径用复数名词，动词不出现（除少数动作子资源）
- [ ] 有版本前缀 `/api/v1`
- [ ] 统一响应结构 `{ code, message, data }`
- [ ] 分页参数与返回结构统一
- [ ] 未登录 401、越权 403、参数错 422
- [ ] **每个涉及资源的接口都校验了资源归属**
- [ ] 写操作考虑幂等
- [ ] 库存 / 名额类用原子更新，无「先查后写」
- [ ] 错误响应不含堆栈与 SQL
- [ ] 文档与实际一致
